## What was automatic

Four fresh kickoff model turns obtained actual native context/assessment results
and successfully called native h2_start. Successful PostToolUse receipts and the
stored task.run binding were checked before stopping initialization. No run was
started by the acceptance controller. Each goal created exactly one new run;
older runs stayed separate and no nested experiment was created.

The two failure scenarios used explicitly supplied, controlled incorrect square
implementations. The **model itself** copied each version, ran the unchanged
checker in a separate command, observed an actual AssertionError / exit 1 and
recorded native feedback under distinct attempt IDs. Receipts retain the two
different source SHA-256 values. The controller did not manufacture feedback.
The goal stayed simple/standard, so escalation came from the two failures rather
than reclassifying it as complex. The original task/domain/task_key stayed the
same through the failure chain, bound candidate sessions and final closeout.
Identity includes the project namespace: identical goal keys in two projects do
not share failure state.

The controller pre-created the lightweight identity for the failure fixtures;
their first-touch natural assessment is therefore not an acceptance claim. The
complex scenarios independently cover first-touch natural assessment. Supplied
faults are not evidence that the model naturally produced those defects.

## What was executed after startup

After automatic initialization, the controller scheduled **16 fresh top-level
model sessions**, four for each run: baseline, general, domain and composed. Each used
its own verified candidate workspace and the same frozen inputs/checkers. Every
session restored the parent's original goal, with no new experiment or outer
feedback inside the candidate. The checks verify configuration parsing,
quote-aware comments, duplicate source locations, scalar types, round trips and
legacy compatibility, or integer-square semantics, according to the fixture.

All 16 actual probes passed. Four independent validation commands then passed.
There was no supported quality advantage for composition, so all four runs
retained the passing baseline. The composed harness instructed workspace-local
scratch after earlier traces showed fixed shared `/tmp` hash manifest names;
composed command traces contained no shared `/tmp` references. This is an
observed workflow adjustment, not a model-quality gain. No prior candidate
answer was copied to create another execution.

The selected artifacts were applied to the synthetic business targets and four
separate outer checks passed. Business-output SHA-256 values were bound to the
retained adopted artifacts before/after checking and after feedback. New passed
events supplied every frozen input hash as validated_inputs; native readback
returned reuse with source_baseline.kind=reported_outer_validation and no
UNKNOWN stage. Failure streaks cleared after success, while both original
failed events remained byte-for-byte equivalent in each history.

## Preservation and limits

- Existing fixtures include real Git commits, a verified historical v0.2.1 run,
  its library entry and a user-owned dirty sentinel. Their old files stayed
  unchanged; Git HEAD and raw index hashes stayed unchanged as well.
- 20,188 earlier evidence files were hash-checked unchanged. Plugin code was
  unchanged. Only test-created trust entries for the four fixture roots were
  removed afterward; original configuration semantics were restored.
- An initial controller preflight expected the previous count of 14 hooks and
  correctly stopped before a model turn when the real profile exposed 11. That
  nonpassing control was retained; hook configuration was not altered to pass.
- One existing complex kickoff first used a provisional English description,
  then adopted the explicit frozen TASK identity before binding its run. Both
  assessment records remain. No failure or experiment belonged to the unbound
  description; every bound executor and closeout kept the canonical identity.
- Automatic startup and controller-scheduled completion are separate claims.
  This does not establish that the initial model autonomously orchestrated all
  four executions, universal trigger coverage, OS isolation or general quality
  improvement. The acceptance controller performed no production deployment or
  promotion into permanent memory.
